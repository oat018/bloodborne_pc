## What upstream has and does not have

Upstream has general PSN/networking, Matching2, signaling, parties and P2P transport. Its `gpu/bbnet/SHADNET-PORT.md`, vendor tree, `thd/` implementation and `bbnet_glue.cpp` concern ShadNet/ShadPS4 integration. The pinned tree has no BBSC symbols in `gpu/CMakeLists.txt`, `gpu/bbnet/`, or `tests/`; it has no BBSC game hooks, policy, party persistence, journal, save receipts, Bloodborne-specific catalogs, or BBSC tests. This is not evidence that networking supplies seamless-co-op behavior.

The old BBSC runtime calls into its own forked ShadPS4 code and Linux bbport shim. Preserve BBSC behavior as portable policy where possible, but rebind it to upstream's actual network/runtime callers. Do not transplant the old vendor subtree or `gpu/bbnet/CMakeLists.txt` wholesale.

## Upstream registration and callers

At the upstream pin, `gpu/CMakeLists.txt:189` adds `bbnet/bbnet_glue.cpp` to the static target, and `target_link_libraries(bbgpu PUBLIC bbnet)` links the target (around lines 210-240). `gpu/bbgpu.h:20-24` declares the C entrypoints; `src/probe.c:509,681,717` calls `bbnet_configure`, `bbnet_set_image`, and `bbnet_initialize`; `gpu/shim/bbgpu.cpp:267-273` declares and calls `bbnet_register`. Implementations are in `gpu/bbnet/bbnet_glue.cpp:440-464`. These symbols establish upstream's static integration lifecycle. In particular, `bbnet_initialize` initializes ShadNet runtime/NP state and `bbnet_set_image` forwards the image to `BbThd::SetImage`; neither is a BBSC hook or evidence of admission timing. Upstream's build entry point is root `build.sh`; Windows instructions are in `packaging/windows/README.md`. Its test tree contains generic runtime/GPU tests, but none of the old BBSC tests or targets. Old tests were intentionally excluded from default builds and only selected test targets were registered through old bbnet CMake.

Verified lifecycle mapping: upstream GPU initialization calls `bbnet_register` (`gpu/shim/bbgpu.cpp:267-273`); probe setup calls `bbnet_configure`, then passes the loaded image through `bbnet_set_image`, then calls `bbnet_initialize` (`src/probe.c:509,681,717`). Exact BBSC placement within this lifecycle is still a proposal. Party events/transport may map to upstream `thd/` and P2P transport, but no BBSC callers exist there. Admission must be attached to the concrete Matching2/signaling consumer only after call order proves it can reject before Lua join, multiplayer initialization, placement, or reload. Game/save hooks require supported-image, memory, and Windows save callback evidence. Merely finding analogous upstream APIs is not proof of call order.

### Static lifecycle, image setup, and game-thread dispatch

At the upstream pin, static integration has two distinct entry paths:

- `src/probe.c` calls `bbnet_configure(app0, serial, title, version)` during title setup, `bbnet_set_image(image, size)` after loading the executable image, then `bbnet_initialize()` to start online runtime. Definitions are `gpu/bbnet/bbnet_glue.cpp:440-464`; `bbnet_set_image` only forwards to `BbThd::SetImage`.
- `gpu/shim/bbgpu.cpp:267-273` calls `bbnet_register`, which registers exported library symbols. This is a static resolver registration path; `bbnet_initialize` separately initializes NP/network runtime.

The upstream network dispatcher (`gpu/bbnet/thd/thd_session.cpp:313-348`) is a background runtime thread; its `DispatchAfter` queue is not a game-thread scheduler. `thd::SetImage` (`thd_session.cpp:890+`) stores the guest image for its Matching2/signaling hook logic, and `thd` references the image and a hard-coded signaling gate. Neither establishes a Bloodborne game tick. No BBSC per-frame callback, BBSC game-thread marshal, save receipt host callback, or UI hook exists in the upstream tree. The old `bloodborne_re.cpp` game-tick hook was reached by native guest code hook dispatch and ran its `TickBbsc*` functions synchronously in that callback. Do not route these actions to the `thd` dispatcher.

Step 1 discovery tasks: trace when the image pointer remains valid and whether it is relocated; find the pinned base's supported guest-code hook/tick registration and callback threading; establish a safe network-to-game queue with bounded ownership/lifetime; identify unload/reload/shutdown behavior; and prove initialization order relative to Bloodborne library calls. A fixture can test queue ordering and stale-session rejection, but only the built Windows runtime and a live copied profile can establish actual callback thread, tick cadence, image lifetime, and entry timing.

### Native ABI and code-patching contracts

The upstream's `PS4_SYSV_ABI` macro in `gpu/shadps4/common/types.h:28` is `__attribute__((sysv_abi))`; the network handlers use it for emulated PS4 exports (for example `gpu/bbnet/thd/thd_np.cpp`). That annotation does not establish the calling convention for native Bloodborne machine-code hooks or for Windows host callbacks. The old native patch code lives in `bloodborne_re.cpp` and uses offset/byte-site tables, guest register snapshots, trampolines, and writable-code helpers; `src/probe.c` flushes the instruction cache for its own runtime patches, while upstream's own `src/probe.c`/`src/runtime_memory.c` implement Windows `VirtualProtect` and `FlushInstructionCache` paths. These are infrastructure clues, not proof that old hook sites/signatures or protection transitions are valid.

Unresolved discovery contracts: which upstream hook primitive is supported for guest executable code; exact target signatures/register preservation/stack alignment and callback ABI for each hook; whether callbacks can re-enter the emulator or race image unload; Windows page-protection restoration and instruction-cache requirements; and how hooks are removed or invalidated on image replacement. Static analysis and synthetic byte-buffer tests can validate decoders and patch-table matching. Only a live game with the pinned executable revision can validate native offsets, ABI, hook ordering, and safe execution. Keep native managed admission disabled until those are proven.

### Save receipt boundary and UI controls

At the historical pin, `src/runtime_file.c:do_close` is the receipt publication boundary for a dirty character-save write. It snapshots/hashes the temporary image before commit, flushes the writer (`fsync_retry` in `commit_file`), closes it, atomically renames the temp file over the selected path, syncs the parent directory, and only then calls `note_save_close` to increment/publish the generation/hash/byte count on success under `receipt_lock`. `runtime_file_save_receipt` reads that in-memory receipt; `runtime_net.c` supplies it to the module host; Bloodborne code calls `ReadBbscSelectedSaveReceipt` for `/savedata0/userdataNNNN`. Direct in-memory mutation, a save request, write completion before close, or a successful game-side callback is not this receipt. The old POSIX `fsync`/directory-fsync/rename guarantees cannot be copied into a Windows implementation by name alone.

Offline fixtures can test receipt decisions using temporary files, interrupted writes, identity changes and mocked commit/flush failures. Windows-native tests must later establish `FlushFileBuffers`/replacement/directory metadata behavior and profile selection. Live copied-save gameplay is required to prove which save writer, selected slot, serializer, and close/receipt sequence the game actually uses; offline fixtures cannot prove that call chain.

User-facing controls in the historical runtime are distributed across game and overlay code, not exposed as a single settings screen. Bloodborne's own co-op sign/Matching2 room data carries the password/matchmaking interaction. The Silencing Blank (goods 111) is the guest departure control observed by `TickBbscBlank`; host Blank handling has separate `TickBbscHostBlank` logic. Preserve the approved Parting Blank menu behavior: the native menu can stop the bell signal or end co-op, and the Kit row retains the native menu/dialog, leave effect 7, and animation 15; the compatibility hook supplies the native Blank-use discriminator for item 11251. Native item/event hooks in `bloodborne_re.cpp` detect these actions; `TickBbscSessionEnd` and related return logic process them. The migration requirements also include unsupported-area explanation and normal game text/animation. The old port's ImGui loading overlay (`ShowLoadingScreen`/`HideLoadingScreen`) was forwarded by `bbsc_glue.cpp` to `bbgpu_overlay_banner`; `StartIntro` was a no-op although the header describes an optional title intro. Upstream does not provide these BBSC controls or their overlay API. Identify upstream menu/sign ownership, overlay host/call thread, localization/text and animation paths before implementing; do not invent an upstream API or treat the no-op intro as a working feature. Game-play controls, text/animation and placement behavior require live copied-profile checks; pure Blank policy/session state can use fixtures.

## Adapter contracts to discover

No adapter API is defined yet. Before defining one, identify the concrete upstream owners and lifecycle for: BBSC opt-in/title policy; authenticated peer/session-bound transport; network-to-game-thread delivery; image identity and supported hook installation; selected profile/save identity; save commit, durable receipt and recovery; and menu/text/animation requests. Record each real caller and callback ordering, thread, lifetime and failure result first. Keep portable party/session policy, protocol validation, eligibility, additive-progress decisions, journal/receipt decisions and recovery intent separable from upstream internals, but let the source findings determine interface shape.

In particular, an admission decision must be invoked by the actual consumer before Lua join, multiplayer initialization, placement, or reload. The current upstream call and alternate paths remain unproven; do not name or implement a `BeforeJoin` API until that consumer and its ordering are located. No hypothetical adapter signature is evidence of a working hook.

## Selective patch order

1. Establish and record pinned clean Windows upstream baseline per plan step 2; do not mix BBSC code into it.
2. Add portable BBSC policy units (party/session/events, protocol checks, journal/receipt decisions) and migrate their tests; no native hook registration.
3. Add upstream static CMake registration and the BBSC adapter interface; initialize only under explicit BBSC opt-in, preserving default network behavior.
4. Adapt networking in small files/hunks: authenticated private attempt and peer binding; Matching2 admission before side effects; correlated cleanup; existing party transport; departure paths. Retain upstream vendor files and compare every touched hunk against the pinned revision.
5. Port selected-profile durable save primitives and receipts with Windows semantics/tests; keep recovery pending when profile or identity is ambiguous.
6. Add image/memory adapter after native version evidence; separately establish admission rejection and first-playable boundary before enabling managed joins.
7. Integrate additive progress and safe return behind durable receipts/recovery fences; verify before broad runtime enablement.

## Evidence gaps and limits

- Native upstream baseline build, copied-profile gameplay and selected no-game Windows fixtures now have evidence in the setup report/test matrix. The historical BBSC runtime has not been integrated or built on the new upstream, and five upstream test targets have recorded Windows compile failures.
- No current upstream caller trace proves a pre-side-effect Matching2 admission point across all request, callback, Lua, reload, placement and alternate-room paths. Step 1 discovery must name the exact consumer and ordering before proposing a hook.
- No upstream BBSC game tick or game-thread scheduler was found. Trace the supported guest-code hook/tick path, network callback handoff, image lifetime, shutdown and callback re-entry before attaching BBSC work.
- No supported CUSA03173 1.09 native hook signatures, offsets, register/stack contracts, Windows host/native ABI, protection restoration, instruction-cache ordering, or hook teardown behavior was validated. Do not port old offsets based only on byte fixtures.
- No upstream selected-save writer, serializer/grant completion callback, durable receipt service, profile/save identity mapping, or atomic replacement/flush contract was identified. Map the concrete writer→close→durability→receipt path; keep pending recovery if identity or completion is ambiguous.
- No upstream BBSC UI controls/overlay service were identified. Discover where game signs/Blank actions enter, how normal item animations/text are preserved, where unsupported destinations can be explained, and which host/guest departure paths reach the UI and return handlers.
- Windows fixture coverage may establish portable protocol encoding, state machines, correlation/expiry/retry, identity key algorithms, journal recovery decisions, and mocked receipt failure handling. It cannot establish real hook ABI/order, actual save selection/flush behavior, menu animation/text, party placement, or gameplay. Those require the pinned Windows runtime and copied profiles; private server/peer reachability additionally requires the authorized private network to be available.
- The Python `test_bbsc_character_ids.py` is a gameserver SQLite allocation test. It provides no evidence about local save identity, slot reuse, or NG epochs. Client identity needs separate portable C++ fixtures plus live copied-save evidence for the game's actual slot selection and reuse behavior.
- Historical Linux fixture/test results and gameplay reports are historical evidence only; none qualify Windows validation. This manifest assigns no native offsets and makes no claim of live game validation.
- Historical FSR work stays archived separately. Baseline build applied only the upstream's own FSR patches in its separate checkout. This source audit changes documentation only; no BBSC runtime, server or game state was changed by the planning pass.
