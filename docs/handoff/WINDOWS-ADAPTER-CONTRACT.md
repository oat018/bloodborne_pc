### Image lifetime and protection details

`src/probe.c` allocates the guest image as the loader-owned mapping (image allocation and segment load precede relocation in the image-loading block around `:560-680`). It calls `bbnet_set_image` after relocation at `:681`, before patch-file application at `:682`, trap/image/segment final protection at `:686-696`, module initializers, `bbnet_initialize`, and guest entry. The exposed `bbnet_set_image(unsigned char*,uint64_t)` API (`gpu/bbgpu.h:23-24`) has no status, generation, replacement, or clear operation; `BbThd::SetImage` is only a forwarding target (`bbnet_glue.cpp:460-462`). At `thd_session.cpp:878-916`, SetImage clears `g_image`, rejects null/short images and compares bytes at `kCharaStep-kImageBase` to `kCharaStepPrologue`, then stores the raw pointer. This is a CUSA03173 1.09 signature/offset check in current source, not independently qualified evidence and not a contract for BBSC to reuse. Source does not establish image release or replacement lifetime.

Windows `protect()` in `src/probe.c` is the loader-side final segment protection boundary; `src/runtime_memory.c` owns guest virtual-map protection and Windows view operations (`VirtualProtect`, view map/unmap). Neither API registers BBSC code hooks. `thd_session.cpp:886-914` directly writes `g_image+(kSignalingGate-kImageBase)` when the byte is not `1`; the code does not query/temporarily change/restore page protection there. `SetSignalingGate` is called synchronously by `m2_context_start` (`thd_matching2.cpp:568-570`) while holding `g.mu`, before starting its poller. The call is on the guest API caller thread, but source does not validate its thread identity or prove page writability. Required G1 instrumentation: image base/size/hash and generation at callback; each hook address and expected/replacement bytes; page protection before/after; instruction-cache flush result; callback thread; uninstall/restore result; and proof all queued callbacks drain before image/process teardown. Hook installation failure must leave managed admission disabled. These observed THD offsets are not to be copied or inferred as BBSC adapter contracts.

## Matching2, signaling and admission

### Which implementation is active

`BbThd::Enabled()` is exactly `BB_ONLINE=1 && BB_NET_BACKEND=thd` (`gpu/bbnet/thd/thd_session.cpp:92-95`); absent either exact environment value the vendor implementation is selected. Startup resolver registration runs `bbnet_register` from `gpu/shim/bbgpu.cpp:266-273`. In `gpu/bbnet/bbnet_glue.cpp:464+`, the enabled branch registers THD network/Matching2/NP via `BbThd::Register` then HTTP/HTTP2/SSL2 and returns; it does not register vendor Net/NetCtl/NP/Matching2. The fallback branch registers vendor network and Matching2 libraries. At online start `bbnet_initialize` (`:452-458`) calls `BbThd::Initialize` for THD, otherwise vendor `NpManager::InitializeRuntime`.

Both routes use the same `SymbolsResolver::AddSymbol`, which appends to `g_symbols` (`gpu/shim/bbgpu.cpp:66-75`; declaration/macro `gpu/bbnet/include/core/libraries/libs.h:12-57`). `bbgpu_resolve` scans in insertion order and returns the first NID match (`gpu/shim/bbgpu.cpp:276-282`). The enabled/fallback branch prevents both Matching2 implementations from being registered by this call; common HTTP is registered after the selected route. Any later duplicate NID would silently resolve to the earlier table entry; there is no source evidence of a priority override. The signature/API map below must therefore treat THD as active only under that explicit environment selection, and vendor behavior as the separate fallback.

## W05 reviewed runtime file observation service — 2026-10-21

Source owners are the existing `src/runtime_file.c` `do_close` → `commit_file` and active mount/profile path translation; this adds no game hook or network callback. Independent source review compared `de2e38a` with historical `ea8ac53` and approved a standalone pure-C runtime observation boundary before implementation. Declaration owner: new `src/runtime_file_receipt.h`, exposed through `src/runtime.h`; implementation owner `src/runtime_file.c`.

```c
typedef struct RuntimeFileReceipt {
    uint64_t generation;
    char path[1024];
    int32_t error;
    uint64_t bytes;
    char sha256[65];
} RuntimeFileReceipt;
int32_t runtime_file_save_receipt(const char *guest_or_host_path, RuntimeFileReceipt *out);
```

Contract: output is zero-initialized before validation. Return 0 means a locked observation was found for the exact canonical savedata host file; inspect `error` separately. Positive errno indicates invalid/unresolved path or absent observation. Guest paths require a current active mount; no previous-host fallback. Profile/configure and mount-rebind/unmount invalidate observations, while generation remains process-global monotonic. It is not a native selected-character identity or serializer callback. No dynamic `BbNetHost` ABI is imported and no BBSC native consumer is connected in W05.

For dirty character-save candidates only, serialize competing close/publication work. Check preceding write outcomes including short writes; hash the complete exact temporary candidate while its writer remains open and verify file identity/size. Publish a success observation only after checked file flush, checked writer close, and checked same-volume replacement/write-through operation. Increment generation only on success. A failed attempt invalidates that path's previous successful observation: retain generation, set positive error, clear bytes/hash, preserve the old committed save and pending BBSC work. A clean/no-op/non-character close must not manufacture a success observation. Hash/path/file ownership errors fail closed. Data in a receipt proves candidate file bytes only, never game-event completion or inventory qualification.

Windows qualification is limited to observed successful API operations and tested child-process interruption/reopen behavior. `_commit`/`FlushFileBuffers` and `MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)` do not establish a general power-loss transaction or an independently flushed parent-directory entry for same-volume replacement. Receipt alone cannot retire managed pending progress/return work; that still requires the selected-slot/serializer/grant/identity proof chain and current G2/G3 qualification. Unsupported or ambiguous required proof retains pending work.

Primary references checked during the review: [CRT _commit](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/commit?view=msvc-150), [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers), [reparse operations](https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-points-and-file-operations). Fixture requirements include operation faults, stale/missing receipt, active mount/profile changes, competing processes, and path/reparse swaps. This is an approved implementation contract, not evidence of implementation or a passed native gate.

## W06 reviewed static networking boundary — 2026-10-22

Approved for offline implementation after independent proposal review and two scoped correction rounds; not implemented/native-qualified by this entry. Historical reference is ea8ac53801e49b5dc79c072971c0e05efcd7651f; upstream remains de2e38af055f09f819946951075c6bb119e62ae6. Existing HTTP, Matching2, THD and transport owners remain authoritative. Pure BBSC helpers may live in core/bbsc_network.h and bbsc/bbsc_network.cpp; no dynamic host ABI or guest tick is introduced.

HTTP owns secret summon words and synchronized observation state. Copied public snapshots retain historical sign (generation/valid/session/user/character/type), claim (token/search-generation/valid/unique/password-match/candidate) and private-attempt (state/generation) fields, never secret word bytes. Strings are bounded to128 bytes, candidates64, response1MiB; steady-clock lifetimes are own-sign15min and search/claim30sec. Public observations are not authority to submit a stale request. Reviewed service declarations are:

```cpp
BbscSummonObservationSnapshot GetBbscSummonObservationSnapshot();
std::optional<BbscSummonCapabilityProofSnapshot> GetBbscSummonCapabilityProofs(
    const std::array<u8, 16>& challenge);
std::optional<BbscPrivateJoinAuthorization> ArmBbscPrivateJoin(
    int http_context, u64 matching_request);
bool IsCurrentBbscPrivateJoin(const BbscPrivateJoinAuthorization&);
void FinishBbscPrivateJoin(const BbscPrivateJoinAuthorization&, bool submitted);
```

The opaque authorization binds current HTTP context/attempt/search/claim, selected candidate identity and actual Matching2 request to a monotonic single-use nonce under the observer mutex. Exhaustion fails closed. HTTP context and Matching2 context are different domains: actual source must supply the correct HTTP context or capture it internally, never substitute a Matching2 context id by assumption. Backend request/incarnation state supplies the separate Matching2 context lifetime binding. Do not nest observer locks with Matching2/THD/transport locks. Arm is the authorization linearization point: pre-Arm cancellation denies; cancellation after Arm, including before physical network submission, is an in-flight race requiring current-ticket checks and exact response room/peer cleanup, never current-generation BBSC publication. Host room creation is outside this guest selected-claim gate. Read-only ticket binding accessors may expose nonsecret identity/correlation fields, not construction/mutation or secret words.

Connect-first phases stay distinct: pre-connect eligibility authorizes only a network request; room/owner/connection and challenge proofs are post-response facts. Historical HMAC-SHA256 retains domain BBSC-admission-v1, challenge16, LE-u16-length/session, LE-u64 user/character and LE-u32 summon type; its key remains inside HTTP. Return own/selected32-byte proof plus the atomically corresponding observation, and compare proof bytes constant-time.
